# 結果檢討

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「看到什麼現象 → 代表什麼問題 → 下一次怎麼改」，讓 AI 像店長一樣檢討。

## 什麼時候用

每跑完一次 `npm run simulate`，要決定下一版策略怎麼改時。

## 試算結果裡有哪些線索

試算工具每天會印出：客人數、收入、備貨、宣傳、報廢（清潔費）、淨利、任務、星等、資金，以及「沒買到的客人」：

| 線索 | 意思 |
|---|---|
| 賣完買不到 | 有人想買，但貨不夠 |
| 嫌太貴 | 價格超過客人剩下的預算 |
| 想吃的沒上架 | 客人想吃的菜今天沒賣 |
| 因為討厭的菜不進門 | 上架了某位客人討厭的菜 |

## 對症下藥表

| 看到的現象 | 代表的問題 | 下一次怎麼改 |
|---|---|---|
| 賣完買不到很多 | 備貨太少 | 那樣菜多備一些（注意合計不能超過 80 份） |
| 報廢 15 份以上 | 規則書：報廢 16 份以上會加 50 元大型廚餘清運費，另外每份超過 5 份的部分收 3 元，所以這是會多花錢的訊號。**可能原因（推測）**：某些菜備太多、超過實際想買的人數。用倉庫盤點驗證：看哪一樣菜的「報廢」多、「賣完後沒買到」是不是 0 | 對盤點是「報廢過多」的菜，備貨降到「賣出 ＋ 沒買到」（`suggest`）；先只調 1 到 2 樣 |
| 嫌太貴很多 | 規則書：價格超過客人剩下的預算，客人才不買。**實際觀察**：試算的「嫌太貴」人數。**可能原因（推測）**：某樣菜定價高於客人願意付的錢，但不能只憑這個數字知道是哪一樣菜 | 只挑一樣菜降價（仍要在可定價範圍內），並寫明這樣會犧牲單份收益；下一版看「嫌太貴」有沒有變少、收入有沒有增加 |
| 想吃的沒上架很多 | 規則書：客人想吃的菜沒上架就買不到。**可能原因（推測）**：上架的菜和客人想吃的不一致（最多只能上架 4 樣） | 看是哪一樣菜被想買，換掉一樣賣不動（賣出少、報廢多）的菜來上架；總上架不超過 4 樣 |
| 因為討厭的菜不進門 | 規則書：他討厭的東西有上架，客人直接不進門，也不留評價。**可能原因（推測）**：上架的菜裡有某群客人討厭的，是少賣掉一整批客人，不是價格或備貨的問題 | 比較「因為討厭不進門的人數」和那樣菜自己賣出的份數，再決定要不要下架它；一次只驗證一樣菜 |
| 星等往下掉 | 規則書：星等看滿意和不滿的比例升降；滿意 < 30% 或不滿 ≥ 25% 會降。**實際觀察**：試算每天的「stars」和滿意／不滿人數。**可能原因（推測）**：買不到（賣完、嫌貴、沒上架）造成不滿，或價格高於建議售價使滿意變普通 | 先看是哪種「沒買到」最多，再對應上面幾列調整；星等會影響隔天來客數，所以不要只看當天淨利 |
| 我自己發現的現象：宣傳後增加來客，但淨利未改善 | 規則書：宣傳費 200 元客人 +20%、500 元 +45%，宣傳費要從淨利扣掉。**實際觀察**：先核對三件事——（1）新增收入（宣傳後多進來的客人多買了多少，和上一版或沒宣傳的同一天比）、（2）新增成本（多備的貨、報廢增加的清潔費）、（3）宣傳費本身。**可能原因（推測）**：新增收入沒有超過「宣傳費 ＋ 多備貨的成本 ＋ 增加的報廢」；或多來的客人買到的是沒上架、賣完或嫌貴的菜，所以沒變成收入 | 先寫出算式：新增收入 − 新增備貨成本 − 宣傳費 − 新增清潔費，看是正是負。是負的，就把宣傳費降一級（500→200→0）或不宣傳；只改這一個地方，才知道是不是它造成的 |

## 步驟

1. 讀試算結果，逐天找出上表的現象
2. 每一個現象，照對症下藥表提出一個修改
3. **一次最多改 3 個地方**，這樣才知道是哪個修改有效
4. 把修改後的策略存成新的檔案（例如 `plans/v2.json`），不要覆蓋舊的，方便比較

## 回報格式

```text
這一版的結果：最終資金 …、星等 …、報廢 …
發現的問題：
1. 第 N 天：（現象）→（問題）
修改：
1. …
下一版檔名：
```

## 不准做的事

- 不准修改遊戲檔案（`src/` 底下的任何檔案、客人包）
- 只能新增或修改 `web-lab/plans/` 裡的策略檔
